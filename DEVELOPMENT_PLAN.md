## Статусы и приемка

`запланировано` → `в работе` → `проверка главным агентом` → `ожидает ручной проверки` → `готово`.

Дополнительные статусы: `на доработке`, `заблокировано` (с конкретной причиной), `отменено` (с причиной). Для собственной задачи главный агент может перейти от своей проверки к `готово`, если пользователь не запросил отдельную приемку. Для **любой задачи субагента** этап ручной проверки пользователем обязателен. Отчет субагента сам по себе не означает готовность.

При каждой смене статуса обновлять строку задачи, доказательства проверки и историю ниже. Если меняются требования или порядок работы, менять зависимости и связанные SPEC/архитектуру. В начале каждой новой задачи читать этот файл.

## Проверки при реализации

P-02: субагент владеет только `docs/figma/p02/` и `public/assets/figma/`; главный агент — корневыми документами, `docs/agent-tasks/` и `docs/reviews/`. Поручение сохранено в `docs/agent-tasks/P-02-figma-analysis.md`, точное сообщение запуска — в `docs/agent-tasks/P-02-launch-message.txt`. P-03 и далее не начинать до отдельного поручения пользователя.

Проверка P-02: [отчет главного агента](docs/reviews/P-02.md), [машинный результат](docs/reviews/P-02-validation.json), [пакет субагента](docs/figma/p02/REPORT.md). Все 371 объявления ресурсов из доступных контекстов учтены, 398 связей ассет/узел подтверждены исходным JSX, SHA-256 и форматы всех файлов совпадают. Подтвержденные шрифты/размеры/варианты отделены от предложений по анимациям, breakpoints и 8К.

Для снятия блокировки дозагрузить контексты/референсы Hero Q2/Q3, остальные состояния Button, Navbar/mobile menu/Open, PNG Final Scroll State и доступные prototype/motion после восстановления квоты/доступа. Затем повторить проверку главным агентом и перевести P-02 в `ожидает ручной проверки`. Только явная полная приемка пользователя завершает задачу. Текущий пакет можно проверить вручную по маршруту, но его приемка не закрывает обязательные пробелы. Файлы шрифтов и права веб-использования остаются отдельным открытым вопросом.

- Использовать scripts реального проекта после P-03; сейчас package.json отсутствует, команды не выдумывать. Build обязателен; lint/typecheck — если они доступны или включены в build.
- Новые тесты сначала предложить пользователю. Кандидаты: корректная/неверная загрузка контента, цикл hero и очистка таймера, отсутствие бизнес-действий CTA. Писать после объяснения и в согласованной области; не создавать тесты, зеркалящие разметку.
- Visual/manual: все ширины SPEC, узкая/низкая область, touch, hover, клавиатура, reduced-motion и скрытая вкладка.
- Для обновления контента проверить именно опубликованный JSON в сборке, а не только dev-server.
- Эмуляцию 8К и физическую проверку различать в отчете. Отсутствие нужного устройства фиксировать как ограничение.
- Перед приемкой каждой делегированной части пользователь получает список измененных файлов и сценарии ручной проверки.
